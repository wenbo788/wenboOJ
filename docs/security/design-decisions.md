## ADR-001：公开管理名单页暴露角色布尔值（含 `is_whitelist`）

- **状态**：已采纳（Accepted）
- **日期**：2026-10-14
- **涉及接口**：`GET /judgement/admins`（**无需登录**，公开公示）
- **代码位置**：`service/app/api/judgement.py` → `admin_list()` / `brief()`

### 背景

「管理名单」页用于公开公示站内管理员的职责分工，按「用户管理 / 秩序管理 / 题目管理 / Tag 管理」
四列展示。该页此前只按 `users.can_manage_*` 裸字段筛人，导致白名单 / 超管 / 大管这些**实际拥有权限**
的账号因字段为 `false` 而不显示，公示名单与实际权限不一致。

改造后，四列改为按权限真源（`app.permissions`）判定，并新增返回两个角色布尔值：

```python
"is_big_admin": perm.is_big_admin(u),   # 大管（不含更高层级）
"is_whitelist": perm.is_white_list(u),  # 是否 UID 白名单成员
```

### 决策

**保持现状**：继续在无需登录的公开接口中返回 `is_whitelist` 等角色布尔值。

### 理由

1. **与页面定位一致**：管理名单页本身就是「公示谁在管事」的公开页面，白名单是最高管理角色，
   公开其身份与该页的产品定位相符；隐藏它反而会让公示不完整。
2. **仅暴露角色层级，不含任何凭据或隐私数据**：字段值是布尔量（是否为白名单成员），
   不包含用户名以外的邮箱、手机号、密码哈希、令牌等任何敏感信息。
3. **这些账号的管理员身份本就无法隐藏**：白名单 / 超管在站内的用户名颜色、角色徽章、
   管理操作日志（陶片放逐页 `GET /judgement/logs` 公开可查）等处均已体现其管理身份。

### 风险评估

| 项 | 评估 |
|---|---|
| 风险等级 | **低** |
| 潜在影响 | 攻击者可直接识别最高权限账号，可能针对性尝试密码喷洒、社工或钓鱼 |
| 实际增益 | 有限——白名单成员的管理员身份在站内其他公开位置（徽章、操作日志）同样可见 |
| 数据敏感度 | 无凭据、无 PII，仅角色层级布尔值 |

### 缓解措施

1. **按 IP 速率限制（已实施）**：该接口为公开接口且公示角色身份，必须限制枚举成本。
   实现见 `admin_list()` 首部的 `check(f"ip:judgement-admins:{get_client_ip(request)}", ...)`，
   阈值为 **30 次 / 60 秒 / IP**（`_IP_LIMIT_ADMIN_LIST`，宽松到不影响正常浏览，
   但足以拦截脚本化抓取）；超限返回 **429**。客户端 IP 取自 `X-Real-IP`（由入口 nginx
   覆盖注入，客户端无法伪造，见 `app/utils/ip.py`）。
2. **登录安全**：最高权限账号应使用强密码；管理后台的敏感操作已有审计日志（陶片放逐页）。
3. **权限真源单一化**：所有鉴权统一走 `app.permissions`，避免出现「名单公示了但实际干不了活」
   或「实际能管但名单上没有」的错位（本 ADR 相伴的改动即为此）。
4. **接口最小化**：该接口只返回管理相关字段，不返回 `email` / `phone` / `hashed_password` /
   `real_name` 等隐私字段（见 `brief()` 的字段白名单实现）。

### 关于 `user_number`（UID）不做脱敏

评审曾建议「非必要时隐藏 UID 映射关系」，此处**有意保留**：管理名单项需要跳转到用户主页
（前端链接为 `/user/{user_number}`），脱敏会直接破坏该功能；且 `user_number` 是站内公开标识
（个人主页 URL、用户搜索结果均可见），本身不构成新增信息泄露。

### 名单口径必须与 `is_any_admin` 对齐（避免漏人）

公开名单的**入选过滤**统一走 `app.permissions.is_any_admin()`（站内「能进后台」的真源，含
`is_admin` 泛管理员），而不是「四列 `can_manage_*` 任一为真」。原因是两者口径不同：
仅 `is_admin=True`（四列皆 false）的泛管理员同样能调用 `PUT /site-settings/announcement`、
`GET /admin/users` 等后台端点——若把他从公示名单里过滤掉，就等于再次制造
「名单与实际权限不一致」，与本节决策的初衷相悖。相应地，候选 SQL 也补了
`User.is_admin == True`，否则会在数据库层就被漏掉。

### 备选方案与回退方式

| 方案 | 取舍 |
|---|---|
| **A. 保持公开 + IP 限流（当前采纳）** | 公示完整、实现简单；已用限流抬高枚举成本 |
| B. 移除 `is_whitelist` 字段，只保留 `is_super_admin` | 可降低白名单身份的显式暴露；但白名单与超管在展示上已被同等对待，收益有限 |
| C. 接口要求登录后可见 | 牺牲公示页的公开性（未登录用户看不到管理名单） |

**回退方式**：若产品上确认白名单身份不宜公开，直接删除 `brief()` 中的 `is_whitelist` 一行即可，
前端已通过 `is_super_admin` 与角色徽章覆盖大部分展示需求，无其他依赖。
